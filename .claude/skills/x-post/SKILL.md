# Writing an X post for Tenderwize

The full house style rules live in `X_POSTS_GUIDELINES.md` in this skill's own directory (`.claude/skills/x-post/X_POSTS_GUIDELINES.md`) — **read that file before drafting anything**, it is the source of truth (voice, structure, formatting, do's/don'ts, pre-publish checklist). This skill only adds the workflow around it.

If the draft will name a Tenderwize feature (the "capability" step of the value-first formula in guidelines section 3), also read `FEATURES.md` in the same directory first — it's the fixed list of what Tenderwize actually does. Never name a feature that isn't on that list.

There is also an in-app AI generator at `admin/x-posts` (backed by `POST /x-posts/adm/generate`) that follows the same guidelines file, saves results as drafts in the database, and auto-renders a branded card image (1200×675, see guidelines section 4) from the post's hook via `POST /x-posts/adm/:id/image`. For Interesting Tender, Market Insight, and Contract Award it queries Tenderwize's real tender/award data itself (via LLM tool-calling against MongoDB) and refuses to generate if nothing real matches the topic — it never invents facts. This skill is for conversational drafting/review in chat — it does not write to the database, render images, or run that tool-calling pipeline. If the user wants the result persisted as a draft (with its image and verified data), tell them to run it through the admin panel's "Generate" form (same topic/pillar/notes), or paste your draft into the "extra notes" field there.

Contract Award also has a **story angle** picker (Auto / Company Story) — a second level within the pillar, see guidelines section 3 "Story angles". Company Story is a three-stage pipeline: (1) the backend deterministically scores eight specific patterns (growth, acceleration, repeat buyer, buyer/market expansion, exceptional win, specialization, milestone) across a supplier's *entire* award history and keeps only candidates scoring ≥0.70; (2) it then searches the open web (Brave Search, restricted to official/gov/EU/curated-press sources) for real corroborating context on the specific award/buyer the pattern is anchored on, extracting only facts literally present in fetched pages, each with a verified `sourceUrl` — a candidate the web can't corroborate is treated as no story at all; (3) only then does the AI phrase the confirmed pattern (plus any verified external facts) into a post — it never searches for or judges a pattern itself. A bare two-point contrast (largest vs. latest award, first vs. latest, "€800k then €3,625") is explicitly NOT a valid pattern on its own — see "Meaningful Narrative Rule" in the guidelines. Also note "Pattern confidence ≠ storyworthiness" — a mathematically strong pattern (e.g. a pharma company's awards being 98% pharmaceutical) isn't automatically interesting if it's unsurprising. When drafting a Company Story by hand in chat (no backend detector/enrichment available), apply the same discipline yourself: only claim a pattern if it's backed by ≥3 comparable observations or a real baseline comparison, verify any external context against its actual source before citing it, and use the same wording hedge as the generator — never claim a company's *total* contract history, only what's found in Tenderwize's data.

## Workflow

1. **Identify the pillar.** If the user didn't say which of the five post types they want, ask, or infer it from what they're describing:
   - 🔥 **Interesting Tender** — one specific, currently open tender. The admin generator now picks it via the same detect-first pipeline as Company Story (see guidelines section 3 "Pattern detection") — a large value alone is never the reason, it's *why* the value is large (a Dynamic Purchasing System ceiling, an outlier vs. category median, a short deadline, a rare category, etc.). If a tender is a DPS/framework agreement, its value is a multi-year ceiling, never a single purchase — get this framing right when drafting by hand too.
   - 📊 **Market Insight** — a stat/trend from Tenderwize's own data. The admin generator scans "Overall" plus the top active countries/CPV categories for a real percentage swing (≥40%, with a minimum sample of 5) or genuinely new activity, and only phrases a trend that cleared that bar — see guidelines section 3 "Pattern detection". When drafting by hand, apply the same discipline: never call a swing between two small counts a "surge" or "decline".
   - 🏆 **Contract Award** — a completed award (buyer, winner, amount).
   - 💡 **Procurement Insight** — evergreen educational content, no data needed.
   - 📜 **Historical Story** — a real, verifiable historical business/procurement story (a famous cost overrun, a landmark contract, a scandal). Unlike every other pillar, it has no Tenderwize DB signal at all — grounding is entirely web-enrichment-verified facts (a widened allowlist including Wikipedia/Britannica/national archives). Never write this one from your own training-data memory of the event, even when confident — look up and cite real sources first, same as the admin generator does.

2. **Ground it in real data for the first three pillars.** Never invent a buyer name, amount, CPV code, or deadline.
   - If the user already gave you the specifics (pasted a tender, a number, a notice), use those.
   - Otherwise, look for real data before writing: the local MongoDB (`mongodb://127.0.0.1/<DB_NAME from .env>`, collections `tenders` and `awardtenders`) if you have DB/shell access in this session, or the admin API (`/tenders/adm`, `/x-posts/adm`, etc. — see `admin/app.js` for the calling pattern) if a server + admin token are available. If neither is available, ask the user for the specific facts rather than guessing.
   - For **Interesting Tender**, explicitly check the submission deadline is still in the future before treating it as a live opportunity.
   - **Procurement Insight** needs no data lookup — it's expertise content.
   - **Historical Story** needs a web lookup instead of a DB lookup — find real sources (news archives, Wikipedia, official records) for the specific event before writing, and cite what they actually say rather than your own recollection.

3. **Draft** following `X_POSTS_GUIDELINES.md` section 6 (single post) or section 7 (thread), matching the pillar's specific rules from section 3, and keep the card image in mind (section 4) — the hook (first post) is what gets rendered onto it. If the post links anywhere, follow section 9: use a URL you actually have (from the user, real data you looked up, or a tool result), or one built strictly from a real pattern in the frontend's live `ROUTES.md` (fetch it from `{CLIENT_URL}/ROUTES.md`, or ask the user for its current contents if you can't fetch it) plus a real value you actually looked up — never guess a path or a placeholder value.

4. **Self-check against the pre-publish checklist** (section 12 of the guidelines) before presenting the draft. Fix anything that fails rather than presenting a draft you know breaks a rule.

5. **Present the draft(s)** with the pillar labeled, plus a one-line note on where the facts came from (so the user can verify them). If you wrote a thread, number the posts so the user can see the split.
